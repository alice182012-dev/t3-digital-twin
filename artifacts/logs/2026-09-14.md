The pinned GraphHopper build (`israelhikingmap/graphhopper`, digest pinned in `compose.yml`) rejects any newly-declared vehicle encoded value at startup, before OSM import even runs: `Cannot compile expression: '<name>_access' not available`. `TODOS.md` records the investigation. The failure reproduces identically for `foot_access` (the profile actually wanted) and for a from-scratch `bike_access` test profile with no dependency on `foot`, which rules out anything specific to pedestrian routing or to this OSM extract. It happens inside `GraphHopper.checkProfilesConsistency()`, confirmed by `graph-cache` staying empty and no import log lines, so it isn't a stale-cache or config-syntax problem. Four things were tried and all failed the same way: GraphHopper's bundled `foot.json` verbatim, a trimmed version with `hike_rating`/`mtb_rating` dropped, a further trim dropping `foot_priority`, and the synthetic `bike_test` profile. Root cause is still open: either a different pinned GraphHopper build fixes it, or this needs a diff against upstream's encoded-value factory for this exact snapshot commit. Use `docker compose up --force-recreate graphhopper` for further testing, not a bare `docker run` against the image, which hung at ~100% CPU with no import progress on two separate attempts for unrelated reasons.

The two halves of the fix that don't depend on resolving the GraphHopper issue are already done and inert. `floodmap/graphhopper-flood-road/scripts/flood_utils.py` now has `VEHICLE_PROFILES["foot"]` at a 40cm depth threshold, matching the user's stated pedestrian-blocking requirement, and corrected the `truck` threshold from 50cm to 35cm in the same change. `derive_areas()`/`build_custom_model()` are vehicle-agnostic, so no further backend change is needed once a `foot` profile actually exists on the GraphHopper side. `floodmap/graphhopper-flood-road/graphhopper/foot_custom.json` and `foot_avoid_private_node_custom.json` are staged and commented but not wired into `config.yml`'s `profiles` list: `compose.yml` mounts both files into the container, but the `foot` profile block itself is commented out with an explanation pointing at `TODOS.md`. Once the underlying build issue is fixed, wiring is a roughly 15-minute change: restore the `foot` entries in `config.yml` (profiles, `profiles_lm`, `graph.encoded_values`) and add `foot: {}` back to `graphhopper-maps/config-local.js.example`'s profile list.

`foot_custom.json` is a trimmed copy of GraphHopper's own bundled `foot.json`, dropping `hike_rating`/`mtb_rating` (gate tags this Hanoi extract doesn't carry, same reasoning as `truck_custom.json` dropping `turn_costs`) and `foot_priority` (fails to compile on this build even when listed in `graph.encoded_values`), falling back to a flat access/speed gate shaped like `car_custom.json` and `truck_custom.json`. `foot_avoid_private_node_custom.json` is a verbatim copy of GraphHopper's `foot_avoid_private_node.json`. Both got the `_custom` suffix because the unsuffixed names are reserved for GraphHopper's built-in profiles, the same reason `car.json`/`truck.json` became `car_custom.json`/`truck_custom.json`.

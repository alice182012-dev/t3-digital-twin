# Workspace log — 2026-09-18

## Summary of 2026-09-17

Two raster-only fixes for the flood tile's fragmented look (pixel dilation, default zoom 13
to 17) both shipped and were reviewed side by side. The user then flagged a wide river channel
that still rendered as scattered blue blocks instead of a continuous flooded stretch, ruling
out "sparse hydrology" as the full explanation and out both fixes as sufficient on their own.

A code review confirmed the tile-rendering path (`tiles.py`) is display-only: routing reads
depth from the PostGIS table `flood_road_values`, not from tile pixels, and no depth-at-point
UI panel exists yet. That cleared the way to treat tile appearance as a pure display problem,
with no hazard or routing risk from changing it.

Decision: try vectorizing the depth raster into smooth polygons, the way the UK Environment
Agency's "Flood map for planning" renders flood extent, before building a vector layer into the
app. The manual QGIS workflow is written up at `artifacts/docs/qgis-vectorize-flood-depth.md`:
threshold to a wet/dry mask, close the mask to merge nearby wet cells, polygonize with
8-connectedness, simplify and smooth, export to GeoJSON.

Separately, the app's depth palette moved from 5 bands to 8 (floors at 1, 5, 10, 20, 30, 40, 50,
and 60 cm), keeping the two colors from the approved mockup and linearly interpolating the six
new ones between them. `tiles.py`, `depthScale.ts`, and `test_tiles.py` are updated and passing;
the mockup HTML itself still shows the old 5-band legend and needs a separate redesign pass.

## Suggestion: cut depth_by_polygon.geojson down before the next vectorize pass

The GRASS closing workflow above ran once end to end and exported
`artifacts/docs/depth_by_polygon.geojson`: 458 MB, 338,464 features, each carrying only `fid`
and a `DN` band code. A render of that file (`flood-mode.jpg`, shared 2026-09-18) shows why it's
that large: hundreds of small isolated specks and doughnut-shaped holes inside the wet area,
each one its own polygon, not the smooth Environment-Agency-style extent the workflow is aiming
for. Loading a file this size as a vector layer in the frontend isn't viable regardless of shape.

Try these changes, in this order, on the next GRASS run:

1. **Raise the closing radius.** The doc's `R` parameter controls how many cells the
   `r.grow.distance` and `r.mapcalc` grow/shrink pair merges across. The last run used `R = 3`.
   Try `R = 8` to `R = 10` first. Most of the speckles in `flood-mode.jpg` are isolated wet
   cells a radius of 3 doesn't reach.
2. **Dissolve before simplifying.** Run `native:dissolve` on the polygonized layer, grouped by
   `DN`, so every polygon in one depth band merges into a single multipart feature instead of
   staying as one feature per pixel cluster. This is what actually drops the feature count from
   the hundreds of thousands to the dozens; a bigger closing radius alone won't do it.
3. **Delete holes and small slivers.** Run `native:deleteholes` with a minimum area threshold
   (start at 20 to 50 m²) on the dissolved layer, and drop any remaining polygon under that same
   threshold before export. This removes the doughnut holes and the smallest specks that survive
   closing and dissolve.
4. **Widen the simplify tolerance.** The doc's 1 to 2 m tolerance (1 to 2 times the source
   raster's pixel size) barely simplifies anything. Since this layer is for display, not
   analysis, try 3 to 5 m.
5. **Smooth last.** Run the doc's existing smooth step (2 to 3 iterations, offset 0.25) after
   dissolve and simplify, not before, so it smooths one shape per band instead of thousands of
   small ones.

Run order: close (`R = 8`-`10`) -> polygonize -> dissolve by `DN` -> delete holes and small
polygons -> simplify (3 to 5 m) -> smooth. Compare the result against `flood-mode.jpg` and check
the exported file's feature count and size before deciding whether it's small enough to serve to
the frontend as a vector layer.

No GDAL or GRASS command-line equivalent of this run was executed today; `qgis_process` isn't
installed on this Mac (see 2026-09-17's note on its broken numpy import), so the plan above
assumes the same manual QGIS Processing Toolbox workflow as the last run, with the parameter
and step-order changes listed.

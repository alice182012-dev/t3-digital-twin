# Workspace log 2026-09-24

## Summary of 2026-09-23

The `foot` routing profile blocker was root-caused and fixed: the GraphHopper entrypoint ignored the
mounted graph cache until `-o /data/graph-cache` was added. A missing `geom_4326` column that broke
routing for every profile was also fixed. The day then produced two draft PRDs, sixteen user stories in a
three-sprint plan, seven lessons, and the `refresh-artifacts` skill. In the evening, delegates built the
TimescaleDB schema and service, the two frontend polish stories, `GET /flood/points`, and the flood metric
extractor. Server checks on 2026-09-24 (recorded at the end of that log) marked five stories `Done`.

## Raster-first plan and its first stories

Chose to retire the GeoJSON chain (tasks 4 to 8) from `flood_mapping_full` and make the PostGIS depth raster
the source of truth. The plan is [[raster-first-flood-pipeline]], with five stories in Sprint 2
([[raster-first-pipeline-stories]]). Three were built by delegates and merged locally:

- `road_segment`: 35,652 pieces of at most 50 m from 12,431 ways, keyed by OSM way id (`Reviewed`).
- Tiled rasters: 256 by 256 tiles behind a spatial index, with retention of the newest 3 runs (`Reviewed`).
- The DAG retirement and the netcdf schema fix: built and loaded in a real `DagBag` on the server, but
  **not merged**, because after it nothing writes `flood_road_values` until Story 3.

## Stage A deployed

Pushed `flood-on-points` (`6155f09`) and deployed everything except the DAG retirement.

- `flood_mapping_full` was already paused, so I left it paused.
- Created `flood_depth_raster_tile` with `create_flood_depth_raster_tables.py` (run twice, idempotent).
- The server-side build failed with "A specified logon session does not exist": Docker's credential helper
  cannot reach the Windows credential store in an SSH session. Built the images from the Mac with
  `docker compose build`, then recreated only `floodmap-backend` and `flood-routing-frontend` on the
  server with `--no-deps`. Every other service kept its uptime.
- Loaded the run `20260924T153638` (4 timesteps, 880 tiles each, 93 MB) with the new loader in 67 s.
- `GET /flood/points` returned 404 before the load and the same values as before after it. On the server a
  tile lookup takes a median of 0.56 ms in the database, against 80 to 280 ms for the whole raster, and a
  full request takes about 81 ms because each request opens a connection
  ([[flood-points-connection-per-request]]).
- Place search works again with the `en` default ([[photon-rejects-vi-locale]]), but results from Ottawa
  and Munich appear next to Hanoi.

Evidence is in `docs/user-stories/evidence/` (`raster-tiles-server-check.png`, `frontend-en-geocoder-check.png`).

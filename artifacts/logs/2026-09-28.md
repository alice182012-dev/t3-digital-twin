## Ran the Stage 2 overlap test, found a real contention bug

Set `FLOOD_TEST_RAIN_MM_HR=50` and unpaused `flood_mapping_full` on its real 15-minute schedule.
Two runs overlapped as intended, both succeeded, but every run under overlap took 20 to 37 minutes
instead of the roughly 14-minute Stage 1 baseline, and the delay grew on each further overlapping
run. `dags/flood_mapping_dag.py` set no Airflow `pool` on any task, so a new run's
`0_check_forecast_rain` queued behind the previous run's entire remaining pipeline on the shared
`AIRFLOW__CELERY__WORKER_CONCURRENCY=2` worker. 3Di itself was not the bottleneck:
`run_forecast_process` blocks on `monitor_simulation()` until the simulation genuinely finishes,
and nothing in that code checks for another active simulation.

Logged as [[flood-mapping-full-worker-concurrency-serializes-runs]] and fixed in two parts, both
deployed to `main`:

- A `threedi_trigger` pool (2 slots) for `0_check_forecast_rain` and `1_trigger_simulation`
  (`16bcf44`). Two false starts on the way there: a first attempt self-provisioned the pool at
  DAG-parse time and failed silently on a missing `include_deferred` value (`c14e55d`), and even
  after that fix the pool still never appeared, because Airflow 3 forbids any direct database
  access from code that runs at parse time. Dropped the self-provisioning function and created the
  pool once by hand instead (`2467c50`), the same out-of-band pattern this repo already uses for
  its schema scripts.
- A `depth_calc` pool (1 slot) for `3_calculate_depth`, paired with raising
  `AIRFLOW__CELERY__WORKER_CONCURRENCY` from 2 to 4 (`26b6133`). Checked the server's real capacity
  first (6 cores, 12 logical processors): `3_calculate_depth` is the only heavy task with real
  CPU-bound multiprocessing (`MAX_WORKERS=8` subprocesses), so it is the one task that can actually
  oversubscribe the box if two of it run at once.

Reviewed four consecutive real runs after the deploy. Both fixes held: every run's
`1_trigger_simulation` started within seconds of its rain check regardless of what the previous
run was still doing, no two `3_calculate_depth` tasks ever overlapped, and run duration flattened
to a consistent 17 to 18 minutes instead of continuing to grow. [[flood-mapping-full-worker-concurrency-serializes-runs]]
is resolved.

What is left is a smaller, different problem: each run's own critical path (trigger about
3.5 minutes, depth calc about 7, raster load about 2.3, tile build about 6) still adds to a little
more than the 15-minute cycle, so a step's tile publishes 1.5 to 3 minutes after its target moment
instead of with the design's intended margin before it. That is latency, not contention, and it is
tracked in [[five-minute-tile-freshness]] rather than reopening this blocker.

## Researched time-aware routing before touching item 5

Spun up two parallel research subagents rather than guessing at a design for
[[routing-not-time-aware]]: one on how Google Maps and Waze handle routing around a hazard whose
availability changes over time, one on the academic time-dependent shortest path (TDSP) literature.
Neither product checks a hazard against the traveller's predicted arrival time; a hazard is a binary
closure for as long as it's active, and Waze's live re-routing is the closest real-world analogue to
recomputing as conditions change. The academic side found the opposite framing useful: a flood
closure satisfies the FIFO condition that makes time-dependent Dijkstra and A* exact and no more
expensive than static Dijkstra (Kaufman & Smith 1993), and Kleff et al. (SEA 2020) solve the
structurally identical "roads closed during time windows" problem in about a second per query.
Option B (route now, compute arrival times, re-route if wrong) has no theoretical backing in either
pass: no paper analyzes it, and it can both fail to converge and miss a route that's only valid
because of good timing. Both passes independently converged on the same shape of fix, a
"time-windowed worst case" that bounds each segment's check to `[earliest possible arrival,
now + trip bound]` instead of one flat window, without either agent seeing the other's answer.
Recorded the full synthesis on the blocker page; still open is the user's actual decision on which
approach to build and the trip-time bound.

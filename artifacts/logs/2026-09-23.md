## Resolved: pinned GraphHopper build rejects any new vehicle profile

Root-caused and fixed the `foot` (walking) routing profile blocker open since 2026-09-14
([[graphhopper-vehicle-profile-rejection]]). Four prior approaches had all diagnosed from the
Java-side error and `config.yml`, and concluded the pinned `israelhikingmap/graphhopper` image
itself rejected any new vehicle encoded value at startup. The actual cause was in the image's
entrypoint script, `graphhopper.sh`: it always injects `-Ddw.graphhopper.graph.location` as a JVM
system property, defaulting to `/data/default-gh` unless `-o <dir>` is passed on the command line,
and that override wins over `config.yml`'s own `graph.location: /data/graph-cache`.
`compose.yml`'s entrypoint never passed `-o`, so the app always loaded a graph frozen into the
image at `/data/default-gh` (only `car_access`/`hgv`/friends encoded), and the real mounted
`graph-cache` volume was never used at all — which is why every earlier attempt saw the cache stay
empty and read that as evidence the failure predated import.

Fix: added `-o /data/graph-cache` to the `graphhopper` service's `entrypoint` in `compose.yml`.
Verified live on the remote host (`100.67.84.55`, `airflow_new` compose project) in three steps:
the entrypoint change alone triggered a real import and kept the three existing profiles working;
restoring `foot` to `config.yml` without wiping the now-populated cache reproduced the original
failure one layer later (same mechanism: loading an already-imported graph that also lacks the new
encoded value); wiping `/data/graph-cache`'s contents and recreating with `foot` in place completed
a real import, registered `foot` with its three new encoded values, and returned an actual
turn-by-turn walking route between two `/nearest`-snapped points.

Landed: `compose.yml` (entrypoint), `graphhopper/config.yml` (restored `foot` profile and encoded
values), `graphhopper-maps/config-local.js.example` and the gitignored local `config-local.js`
(added `foot: {}`). `artifacts/docs/concepts/graphhopper-backend.md` and
`artifacts/TODOS.md` updated to match.

Also hit and fixed along the way: `docker compose` commands run from this Mac's local checkout
were deriving the Compose project name from the local folder (`t3-digital-twin`) instead of the
real deployed project name (`airflow_new`), which briefly stood up a duplicate, wrongly-scoped
`graphhopper` container that failed to start on a port conflict with the real one. Fixed by adding
`COMPOSE_PROJECT_NAME=airflow_new` to the repo's local, gitignored `.env`, so every
`docker --context remote-server compose ...` invocation from this machine targets the correct
stack going forward.

# Workspace log 2026-09-26

## Summary of 2026-09-25

Stage B of the raster-first pipeline reached the server. The DAG retirement, `flood_on_roads`, and depth as the maximum per road
piece (D-006) were deployed with `flood_mapping_full` paused. The irreversible steps ran with the user's approval: the
`flood-results-full` bucket and the `flood_depth_raster` table were removed. The manual `flood_forecast_consecutive_state_test`
DAG was changed to follow the production steps. Its two-event test showed "Updated 21:40" at 21:22, which led to the blocker
[[map-shows-forecast-not-now]] and a proposed design: a 15-minute clock cycle, tiles for steps 1 and 2 only, and a cross-run
"latest step at or before now" rule.

## Session goal

Write the code for that design (tiling and the flood histogram, not routing), then test it on the server with the user's new
3Di template (42180).

## Built on `fifteen-minute-cycle`

Delegates built five streams and one follow-up fix, merged into one local branch and pushed. Plan:
[[fifteen-minute-cycle-tiles-and-histogram]].

- **Tiles.** `publish_run` tiles only the first `tile_steps` steps (default 2). A new `flood_extent_step` table records a
  step as published after its tiles and polygons are uploaded. `GET /flood/timesteps` returns, for each time, the newest
  run that published it. Retention is 8 runs.
- **Map.** The frontend picks the latest step at or before now and re-picks on every refetch. The legend reads "As of …".
- **Histogram.** `POST /flood/forecast` returns the mean depth along a route per 15-minute time from the raster tiles,
  and a chart in the route panel shows it.
- **DAG.** `flood_mapping_full` runs on `*/15 * * * *` with `max_active_runs=2`. The wait sensor and the timetable plugin are
  gone. Overlapping runs no longer share result or raster file names.
- **`create_simulation.py`.** Each run starts at its clock slot and saves states at 900 s and 1800 s. It attaches the
  saved state to the new simulation. The old code loaded the state ID and never attached it, so every earlier "hotstart" started
  without the previous water ([[hotstart-state-saved-at-end-of-run]]).

## Server test, Stage 1

Deployed the branch, set `TEMPLATE_ID=42180`, recreated the worker, created and backfilled `flood_extent_step`, and rebuilt the
map images. Ran `flood_forecast_consecutive_state_test` (`manual__2026-09-25T17:35:10`): all 14 tasks succeeded.

- The template writes 8 steps per event at 900 s.
- Event 1 timings after trigger: depth for 8 tifs 6:40 (done at +9:26), tiles for steps 1 and 2 published at +11:33 and
  +12:11, flood on roads done at +13:36. Depth scaled about 1.4 times from 4 to 8 tifs. The margin before step 1 becomes now is
  about 3.5 minutes for the tiles and 1.4 minutes for flood on roads. Event 2's tiles took 5:05 because they overlapped other tasks.
- Event 2 logged `[Hotstart, exact] ... offset 0 min`.
- Depth times drifted by seconds (`01:15:02`). Fixed by rounding to the minute (`7f87538`). Not yet re-verified on a fresh run.
- The live page showed "As of 01:10" until 02:45. That is expected: the test tiles only steps 1 and 2 of each event, so the
  timeline has a gap. A production cycle has a tile in every slot.

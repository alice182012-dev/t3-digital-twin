## Analysis

### Background

User-reported symptom: the tile overlay renders as scattered blue speckles across wide areas rather than a smooth/contiguous flood extent, matching a prior complaint on record in `artifacts/block.md` (2026-09-08): *"the tiles and the tif doesnt look the same, the tiles doesnt encounter all of the tif data."*

Investigated against real pipeline data: `grasshopper-routing/flood-timeseries/depth_20260809_202000_215000/depth_20260809_202000.tif`.

**Raster characteristics at this timestep:** 56,000,056 total 1m pixels; only 4,252 have any depth > 0; only 1,424 (0.0025% of the raster) reach the 1cm display-band floor. Real, isolated wet cells scattered across a mostly-dry domain — not a broad contiguous flood. Some of the "fractioned" look is genuinely the real data, not a bug.

**Root cause identified:** every tile read reprojects (source CRS EPSG:3405 differs from every tile's Web Mercator), and rio-tiler's default reprojection resampling is nearest-neighbor, which keeps one arbitrary source pixel per output pixel — for cells this sparse, that drops most of them. Measured directly: a z14 tile (13005/7213) over a known-flooded area showed 3 pixels ≥1cm under nearest-neighbor resampling vs. 55 under max resampling, including the tile's single deepest cell (0.68m), which nearest-neighbor dropped entirely.

`ensure_overviews()` (built lazily on first tile touch, `Resampling.average`) compounded this: GDAL's `build_overviews` doesn't support `Resampling.max` (rasterio raises `ResamplingAlgorithmError`), and GDAL selects the nearest overview level *before* the reprojection warp runs — so an average-built overview would poison a max-resampled read downstream regardless of what the read step does. Averaging is also wrong for safety-relevant data on its own terms: it dilutes real danger toward zero instead of preserving it.

**Fix applied (commit 076b2c0):** removed `ensure_overviews()` entirely, added `reproject_method="max"` to every `Reader.tile()` call, so downsampling always keeps the deepest value in a pixel's footprint instead of an arbitrary or averaged one.

**Verification:** confirmed in isolation (direct `render_tile()` call: 55 opaque pixels for the z14 tile above, up from an implied ~3 before) and live through the rebuilt floodmap-backend container via curl (same tile, same 55-pixel count, 200 status).

**Open issue:** despite this fix, the user reports the same fragmented appearance after rebuild + refresh. Not yet explained.

### Assessment of the fix

The resampling fix is the correct engineering decision. Averaging is a real bug for safety-relevant data — it doesn't just blur the display, it can make a 0.68m cell look shallow or invisible. Max resampling is the right semantics for hazard data: never hide the deepest real value in a pixel's footprint.

**One risk to check before calling this closed:** removing overviews entirely trades correctness for performance. Every tile request, including low-zoom city-wide views, now warps the full 56M-pixel source through a `WarpedVRT` on the fly instead of reading a pre-decimated pyramid level. That's a meaningfully heavier read per tile. Worth load-testing tile latency at low zoom (z8–z11) against the SRS's target of <100ms on CDN cache hit before considering this fully resolved — if it's regressed, the fix has moved the cost from "wrong" to "slow," not eliminated it.

**A way to get correctness and speed back:** the `ResamplingAlgorithmError` is likely a rasterio limitation, not a GDAL one. GDAL's `gdaladdo` CLI has supported `-r max` natively since GDAL 3.1, even though rasterio's `build_overviews()` Python wrapper restricts the `Resampling` enum to a smaller subset that may not include `max`. Worth checking the installed GDAL version and testing `gdaladdo -r max depth.tif 2 4 8 16` (or `gdal_translate -r max`) via subprocess, outside rasterio's binding. If that works, rebuild max-resampled overviews during Worker 1's postprocessing step (GDAL is already in that pipeline) to restore pyramid-read speed without reintroducing the averaging bug.

### The product question has an answer

With 1,424 wet cells out of 56 million, most are physically sub-pixel at any zoom below roughly z16–17 for a 1m grid. Correct max-resampling will render some as a single screen pixel — accurate, but reads as "broken" to a human viewer. The fix isn't more resampling; it's a display-layer minimum feature size: render each above-threshold wet pixel with a small minimum radius (e.g., 2–3px dilation applied only in the color-ramp rendering step, not to underlying values) so isolated dangerous cells stay visible at city zoom without averaging their depth toward zero. This keeps the safety property of the max-resampling fix (never hide real depth) while addressing the actual complaint on record in `block.md`.

### Code review: confirming depth sources, before picking a display fix

Before committing to either display fix, ran a read-only review to confirm two things: does the routing engine's flood cost read depth straight from the GeoTIFF, and does any user-facing depth panel decode depth from a rendered tile pixel instead. This matters because the tile-rendering path is display-only, so it's safe to change its visual fidelity (dilation, morphological closing, vectorization) as long as nothing downstream actually depends on those exact pixels.

**Routing:** does not read the GeoTIFF directly at request time. `flood_areas.py`'s `derive_areas()` (`floodmap/graphhopper-flood-road/backend/flood_areas.py:86-132`) queries the PostGIS table `flood_road_values`, which `build_custom_model()` (lines 141-156) turns into GraphHopper `custom_model.priority` rules. Traced the full ingestion chain in `dags/flood_mapping_dag.py`: `calculate_depth.py` writes the depth GeoTIFFs, `extract_geojson_full.py` converts each raster to a per-cell GeoJSON at full grid resolution (`SAMPLE_RATE=1`, no loss), `mapping_geojson.py` then intersects those cells against the road network and keeps only cells that touch a road segment, and that road-filtered result lands in `flood_road_values` via `geojson_to_pg.py`. So routing depth does trace back to the GeoTIFF with full fidelity, filtered to road-adjacent cells by design, not a bug. No RGB-reversal or tile-derived depth anywhere in this path.

**Click-to-see-depth panel:** does not exist in the current codebase. Grepped the whole `floodmap/` tree for `DepthPanel`, `PointInfo`, `depth-at-point`, and related terms, found nothing. If this feature is expected, it hasn't shipped yet.

**Conclusion:** the tile-rendering path (`tiles.py`) is confirmed to be visualization-only, with no downstream consumer relying on its exact pixel values. Free to prioritize "looks like a coherent flood extent" over "exact per-pixel fidelity" in that path, without any hazard or routing correctness risk. This unblocks vectorization as an option, which wasn't viable if any decision-making code depended on the tile PNGs.

### Decision: try vectorizing the GeoTIFF into polygons

Compared against the two raster tweaks already tried (dilation, z17 zoom), a third option was raised by the user: reference the UK Environment Agency's "Flood map for planning" (flood-map-for-planning.service.gov.uk), which renders flood extent as smooth polygons rather than a per-pixel raster. That map is a different kind of product, a statutory return-period extent from a hydraulic model, generalized into vector polygons, not a raw single-timestep depth grid, but the rendering technique (vectorize the wet mask, then buffer/simplify/smooth) is directly applicable here and would fix both the "isolated dot" and "blocky square pixel" look neither raster-only fix solves.

Decision: try the vectorize approach manually in QGIS first, before committing to building it into the app (new backend endpoint serving GeoJSON, new vector layer on the frontend instead of the PNG tile layer). Wrote up the manual workflow as a standalone how-to: `artifacts/docs/qgis-vectorize-flood-depth.md`. Steps: threshold to a wet/dry mask via Raster Calculator, close the mask (SAGA Morphological Filter or GRASS `r.grow`/`r.grow.distance`) to merge nearby wet cells, polygonize with 8-connectedness, simplify and smooth the resulting shapes, optionally buffer-out/buffer-in to merge remaining gaps, then export to GeoJSON.

## Doc fix: the GRASS closing-step instructions were wrong

The doc's fallback step said to run `r.grow.distance` to grow the mask "by a few cells," then
`r.grow` with a negative distance to shrink it back. Tested against a real reclassified depth
raster (`artifacts/docs/reclassify_depth.tif`) and the output filled the entire raster extent
with real-looking values, corner pixels far outside where the source polygon could plausibly
reach held real depth-like numbers instead of NoData, and the file had no NoData value set at
all.

Root cause: `r.grow.distance` computes the distance to the nearest non-null cell for every
cell in the raster unconditionally, it has no radius parameter, so it fills the whole raster,
not a bounded ring around existing wet pixels. `r.grow`'s negative-radius shrink step in the
original instructions isn't valid either, GRASS has no negative-radius erosion mode.

Corrected recipe, both grow and shrink bounded with `r.mapcalc`:

```
r.grow.distance input=orig distance=dist1 value=val1
r.mapcalc "dilated = if(!isnull(orig), orig, if(dist1 <= R, val1, null()))"
r.mapcalc "inv = if(isnull(dilated), 1, null())"
r.grow.distance input=inv distance=dist2
r.mapcalc "closed = if(dist2 <= R, null(), dilated)"
```

Updated `artifacts/docs/qgis-vectorize-flood-depth.md`'s "Close the mask" section with this
recipe (`r.mapcalc` commands via the GRASS Console or Processing > GRASS GIS, in place of the
old UI-only instructions).

pixels):

## Vision

Baseline scope (accepted, not re-litigated): the 3-phase adaptation plan at
`/Users/maianhtran/.claude/plans/dazzling-percolating-raven.md` — Phase A (chrome:
Map/Flood toggle, legend, search pill, route tabs), Phase B (place-popup depth, now
client-side via ported `point_depth.js` logic instead of a new backend endpoint),
Phase C (per-mode ETA, per-step depth, hourly depth chart).

Chosen implementation approach (from 0C-bis): **Full 3-phase plan, client-side depth
reuse** — port `floodmap/valhalla-flood-road-test/frontend/point_depth.js`'s
point-in-polygon logic client-side (using `FloodStore.state.areas`, already loaded)
instead of building a new `/flood/point` backend endpoint. Depth-displaying features
ship behind a visible "provisional data" disclaimer rather than waiting on the
project's model-revalidation gate (see Premise Concern below) — this was an explicit,
informed tradeoff, not an oversight.

**Correction (post spec-review):** the "no new backend endpoint" claim above requires
one small backend addition, not zero backend work. `derive_areas()`
(`floodmap/graphhopper-flood-road/backend/flood_areas.py:104-118`) currently attaches
only `band`/`multiply_by`/`vehicle_type`/`valid_time`/`run` to each `/flood/areas`
feature — no depth value. Its SQL also dissolves geometries per band range (buffer +
simplify across all matching rows), so there is no single point depth to carry even if
we wanted one. The fix: add a `MAX(v.depth)` (or similar aggregate) to each band's SQL
in `derive_areas()` and include it in `properties` as `max_depth_m` — still a property
addition to the *existing* `/flood/areas` response, not a new endpoint or route, but a
real backend change. The client-side popup then reports "band range, max observed depth
in that polygon" (e.g. "10-30 cm band, up to 24 cm here") rather than a precise
point-sampled value — coarser than the mockup's exact "30 cm," and that granularity
difference should be reflected in the popup copy, not glossed over as equivalent.

**Superseding decision (post spec-review, during 11-section review):** the "client-side
depth reuse" Phase B approach above is REPLACED. During Section 1 (Architecture) of the
11-section review, the nil-state conflation in the polygon-port approach (see Section 1
finding below) led to evaluating a third option: sampling `depth.tif` directly instead of
either a new `/flood/point` endpoint or the polygon port. Verified against actual code:
- `depth.tif` is generated per-timestep by `scripts/calculate_depth.py`
  (`dags/flood_mapping_dag.py` task `3_calculate_depth`) but lands only on the Airflow
  worker's local disk (`data/mapping/output_depths/<run-uuid>/`) — never uploaded
  anywhere the flood-road backend can reach it today.
- The flood-road backend (`floodmap/graphhopper-flood-road/backend/`) has zero
  `rasterio`/GDAL dependency today (`Dockerfile` installs only `psycopg2-binary`) and
  reads exclusively from PostGIS.
- PostGIS is a lossy derivative of the tif, not an equivalent: `extract_geojson_full.py`
  subsamples pixels (`SAMPLE_RATE` stride) and drops shallow cells
  (`MIN_DEPTH_THRESHOLD`); `mapping_geojson.py` keeps only road-intersecting polygons;
  `flood_areas.py` further buffers (22m) and simplifies (3m) at query time. This matches
  `docs/block.md`'s own complaint that "the tiles and the tif doesnt look the same."
- Storage check (real data, not estimate): the user's own `flood-timeseries` sample
  (8 events, Aug–Sep 2026) is 32 tifs / 77MB total, ~2.4MB/tif average. MinIO
  (`compose.yml`) has no quota and no lifecycle/retention policy today for anything
  already uploaded (confirmed via existing GeoJSON uploads, which also never expire) —
  this is a pre-existing gap, not new to this decision.

**Decision: use raster sampling via MinIO, not the polygon port.** New work required:
1. Add a MinIO upload step to the depth-tif pipeline (new bucket/prefix, with a MinIO
   lifecycle expiry rule — e.g. 30-90 days — added at the same time, since nothing
   uploaded to MinIO expires today; the user's NAS backup remains the actual long-term
   archive, so MinIO only needs to hold what the backend might query).
2. Add `rasterio` to the flood-road backend's own Dockerfile (already a pinned
   dependency at the repo's top-level `requirements.txt`, just not installed in this
   container).
3. A `valid_time`/`run` → MinIO object-path resolver (today only PostGIS timestamp
   columns serve this lookup, via `flood_areas.list_runs`/`list_timesteps`).
4. The point-depth popup calls `rasterio.sample()` (or an in-memory equivalent) against
   the resolved tif at the exact clicked coordinate — an exact value, not a band-range
   approximation. This ALSO resolves the nil-state ambiguity from Section 1's finding
   more cleanly than the polygon approach: a raster sample either succeeds with a real
   number, or the coordinate/file genuinely has no data (out of raster extent, or the
   file isn't reachable) — no "which dissolved polygon contains this point" fuzziness.

This makes the `derive_areas()` `MAX(v.depth)` aggregate addition described above
UNNECESSARY — that was only needed to support the (now-superseded) polygon-port
approach. `derive_areas()` stays as-is; it's still used for the `FloodLayer.tsx` overlay
polygons, just not for point depth anymore.

Effort/risk correction: this is now human ~2-3 days / CC ~3-5 hrs for Phase B (not the
~1 day / ~1 hr the polygon port would have cost), because it requires new pipeline
(upload step) and backend (Dockerfile, resolver) infrastructure that doesn't exist
today — a real scope increase, chosen deliberately for accuracy over speed.

### Premise Concern Surfaced (Step 0A/0B)
`docs/designs/floodnav-gtm-wedge.md` (approved office-hours doc, 2026-09-04) names an
unresolved model-drift risk: Hanoi has installed unspecified flood-mitigation
infrastructure and the depth model hasn't been re-validated against 2026 data — depth
numbers "could be confidently wrong." The user's own notes (`docs/block.md`, 2026-09-08)
independently flag depth-tif generation being "weird" and tile/tif mismatches. The user
chose to proceed with the full mockup adaptation anyway, mitigated by a disclaimer (the
only thing actually addressing model-drift) and, separately, a real forecast-recency
signal that addresses staleness but not drift — see the reframing in Scope Decisions
#2. The two risks are distinct and only the disclaimer covers drift.

## Accepted Scope (added to this plan)
- Per-mode ETA pills stay in Phase C as originally scoped.
- `FloodLegend` gets a real forecast-recency indicator (derived from `FloodStoreState`
  timestep metadata — how far the selected timestep is from the latest available run),
  not just a cosmetic "Updated <timestamp>" line. **Threshold/UI spec (added post
  spec-review):** show a neutral state when the selected timestep is the latest run;
  show a visibly distinct "N runs behind latest" state (e.g. amber text/icon) once
  `selectedIndex < timesteps.length - 1`, using the same `FloodTimestep` list already
  in `FloodStoreState`. This is forecast recency only — it does not address model-drift.
- The 5-band depth color scale is factored into `src/floodmap/depthScale.ts` only if
  doing so is nearly free relative to writing it inline in `FloodLegend.tsx` — see
  scope-limited note in Scope Decisions #4.
- Phase B's place-popup depth uses raster sampling via MinIO — see "Superseding
  decision" in Vision above, not the polygon port. Popup shows an exact point-sampled
  value (matching the mockup's "30 cm" precision), not a band-range approximation.
- Depth-displaying features (place popup, per-step depth, hourly chart, legend cm
  labels) all carry a visible "provisional data" disclaimer. **Spec (added post
  spec-review):** a persistent, dismissible banner (not a per-feature badge) reading
  something like "Depth values are estimates from an unvalidated model — do not rely on
  them for safety decisions," shown once per session (dismiss state in
  `sessionStorage`, not `localStorage`, so it reappears next session).
- Place-search autofill (`docs/block.md` item 4, referenced by the baseline plan's
  Phase A verification for mockup `2d`): **status resolved (added post spec-review)** —
  already built. `AddressInputAutocomplete.tsx` exists in the current frontend; the
  baseline plan's Phase A verification checks it against mockup `2d`, it does not build
  it new.

## Outside-Voice Review (post 11-section review)

A fresh-context Claude subagent (Codex not installed) reviewed the reviewed plan for what the
section-by-section process structurally can't catch. Four findings were substantive enough to
re-litigate with the user:

1. **Strategic premise** — the approved `floodnav-gtm-wedge.md` design doc says GreenSM (the only
   committed customer) needs an API data feed, not a citizen map, and this plan polishes the
   citizen map. **User's decision, recorded verbatim:** "the API datafeed can be done later i want
   the map first so i can show the real application for users not just the data since our data is
   not good enough to win." This is a deliberate founder call, not an oversight — the data/model
   isn't confident enough yet to lead with a raw feed, so a working, legible citizen-facing product
   is the near-term goal instead. Proceed with this plan as scoped.
2. **ETA pill load cost** (Scope Decisions #1) — accepted; see the caching fix now folded into the
   baseline plan's Phase C item 9.
3. **TimescaleDB conflict** (Phase C item 11) — accepted; the hourly chart now depends on and reads
   from the Phase 1 backend plan's committed TimescaleDB work rather than a bespoke PostGIS
   aggregation. See the baseline plan's revised item 11.
4. **Phase B alternative (PostGIS nearest-neighbor vs. raster-via-MinIO)** — outside voice's
   critique (precision spent on a disclaimed number) noted, but **kept as decided**: raster-via-
   MinIO stands, precision-vs-disclaimer tension accepted as a known tradeoff, not reworked.
